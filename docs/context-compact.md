# 上下文压缩设计

状态：已实现。落地位置和与设计稿的差异见文末「实现记录」。

`ccc` 现在每次请求都把完整 `history` 发给模型。对话一长就会顶满窗口。这一轮按 Claude Code 主循环里的自动压缩来做：先估算 token，超过阈值就让模型把旧对话收成摘要，再用「摘要 + 必须留下的最近原文」替换发给模型的历史。磁盘上的 `.copy-agent/session.jsonl` 继续追加原文，不删。

## 源码里对应的做法

Claude Code 在每次真正调用模型之前跑 `autoCompactIfNeeded`。它做这几件事：

1. 压缩自己的请求、以及记忆提取那种 fork，不再嵌套压缩，避免死循环。
2. 用上一轮 API 返回的用量，或对消息做估算，和阈值比较。
3. 阈值是有效窗口减去约 1.3 万 token。有效窗口是模型上下文长度，再扣掉最多 2 万 token 给摘要输出。
4. 连续失败 3 次就停止再试。成功则把计数清零。
5. 压缩请求尽量沿用主对话的系统提示、工具列表和消息前缀，好命中已有的 prompt cache。提示词要求只回文本，不要调工具。
6. 压缩请求自己也报 `prompt is too long` 时，丢掉最老的一整轮再试，而不是让用户卡死。
7. 成功后，主循环改用新的消息列表：压缩边界、摘要、需要恢复的附件。原文仍留在会话记录里。
8. 自动压缩失败不打断用户。下一轮再试。手动 `/compact` 失败才把错误直接显示出来。

源码里还有会话记忆压缩、上下文折叠、snip 和 hooks。这一轮只做了压缩；折叠后来单独实现，见 `docs/context-collapse.md`，两者在运行时互斥。

## 这一轮做什么

1. 在 `runAgent` 每次 `llm.complete` 之前判断要不要压缩。
2. 超过阈值时调用同一次会话使用的模型，生成摘要，并替换 `history`。
3. 终端增加 `/compact`。网页在状态栏加一个「压缩」按钮，走同一个函数。
4. 压缩进行时，终端打一行「正在压缩上下文」，网页写入一条 `notice`。
5. 环境变量可以关掉自动压缩，或把窗口改小以便测试。

## 这一轮不做什么

- 不做会话记忆文件代替摘要。
- 不做按单条消息裁剪的 snip。
- 不做压缩前后的 hooks。
- 不在压缩请求里开放工具。模型只能回文本。
- 不压缩 `auto` 分类器自己的请求。分类器仍然只看截断后的最近文本。

## 什么时候压

设：

- `AGENT_CONTEXT_WINDOW`：上下文长度，默认 `128000`。
- 摘要输出预留 `20000`，和源码里的上限一致。
- 自动压缩缓冲 `13000`。

有效窗口 = `AGENT_CONTEXT_WINDOW - 20000`。自动阈值 = 有效窗口 `- 13000`。

估算优先用上一轮接口返回的 `usage.input_tokens`（含缓存读和缓存写）。我们现在的客户端还没把 usage 传出来，实现时要带上。还没有 usage 时，用字符数除以 4，工具参数和工具结果的 JSON 也算进去。

下面几种情况直接跳过：

- 环境变量 `DISABLE_AUTO_COMPACT=1`。手动 `/compact` 仍然可用。
- 环境变量 `DISABLE_COMPACT=1`。自动和手动都停。
- 这次调用的来源是 `compact`。
- 本会话自动压缩已经连续失败 3 次。
- 历史里除了系统提示以外还没有一对完整的用户和助手消息。

手动 `/compact` 不看自动阈值。历史太短、来源是 `compact`、或 `DISABLE_COMPACT=1` 时仍然拒绝，并说明原因。

## 压的时候留什么

不能把「助手刚发出的 tool_use」和「下一条 user 里的 tool_result」拆开。从历史末尾往前保留最近一组已经闭合的来回：

- 最后一条用户文本，以及它后面的助手回复。
- 如果这条助手回复含有 tool_use，就把紧跟着的 tool_result 用户消息也留下。
- 再往前的内容全部进入摘要。

如果留下的尾巴自己已经超过自动阈值的一半，尾巴也进入摘要，压缩后的历史里只剩边界和摘要。

压缩后的 `history` 顺序固定为：

1. 一条本地边界消息，角色用 `user`，正文以 `[compacted]` 开头，标明这是自动还是手动，以及压缩前的估算 token。它不展示成普通聊天气泡。
2. 一条用户消息，正文是摘要。模型下一轮把它当成之前发生过的事。
3. 上面决定保留的最近原文。没有尾巴就到第 2 步结束。

下一次再压缩时，旧边界和旧摘要也属于「更早的内容」，会被收进新摘要。发给模型的历史里只留最新的一条边界和一条摘要。

`.copy-agent/session.jsonl` 不改写。压缩前的消息已经在里面。压缩后再追加边界和摘要，方便以后查原文。

## 摘要请求

用当前的 `LlmClient`，但这次请求不传工具。系统提示仍用主会话的系统提示，消息前缀仍是要被摘要的那段历史，这样接口侧的缓存前缀还能用上。最后另加一条用户消息，要求只回文本，并按这个结构写：

1. 用户明确要做什么。
2. 关键技术决定和用到的接口。
3. 读过或改过的文件，以及重要片段。
4. 出过的错和怎么修的。用户纠正过的地方要保留原话。
5. 还没做完的任务。
6. 压缩发生前正在做的事，和下一步。下一步必须贴着用户最近的要求，不把已经做完的旧任务重新打开。

模型可以先写一段分析，再写摘要。我们只保留摘要正文，分析段丢掉。没有摘要正文，或正文看起来是接口报错，这次压缩算失败。

摘要请求自己返回上下文过长时，按「用户文本 + 其后整段工具来回」分组，丢掉最老的一组再试，最多 3 次。3 次仍失败，就抛出，交给下面的失败处理。

## 失败时

自动压缩失败：`history` 保持原样，连续失败次数加 1，当前这轮继续用原文请求模型。终端和网页各记一条说明，不把这次失败当成用户任务失败。连续 3 次之后，本会话不再自动压，直到用户手动 `/compact` 成功。手动成功会把计数清零。

手动 `/compact` 失败：历史不变，把原因直接告诉用户。

用户中止压缩：历史不变，不增加失败计数。

## 界面

终端：

- 自动压开始时打印「正在压缩上下文」。
- 成功后打印压缩前的估算 token 和压缩后的估算 token。
- `/compact` 立刻走同一条路径。
- `/clear` 仍是清空，不是压缩。

网页：

- 状态栏在压缩期间显示「正在压缩上下文」。
- 成功后插入一条 `notice`，不把摘要当成新的助手回复刷在对话正中。侧栏仍显示当前会话。
- 增加「压缩」按钮，调用 `POST /api/compact`。会话正忙时按钮不可用。

## 测试

- 未过阈值时 `history` 不变，模型请求次数不增加。
- 过阈值时，发给模型的下一次 `messages` 以摘要开头，旧的工具结果不在里面，最近一组闭合的工具来回还在。
- tool_use 和 tool_result 不会被拆到摘要和尾巴两边。
- 摘要响应里的分析段被丢掉。
- 压缩请求返回过长时，丢掉最老一组后再试。
- 自动压缩抛错后，原历史仍用于当前请求，失败计数增加。第 3 次之后不再自动调用压缩。
- `DISABLE_AUTO_COMPACT=1` 时不自动压，`/compact` 仍可用。
- 来源是 `compact` 的调用不会再进入压缩。
- 网页 `POST /api/compact` 在忙时返回 409。

## 实现记录

代码：

- `src/agent/compact.ts`：阈值、估算、尾巴选择、摘要请求、PTL 重试、手动入口。
- `src/agent/loop.ts`：每次 `llm.complete` 之前跑自动压缩；失败只记计数，不打断这一轮。
- `src/llm/client.ts`：解析 Anthropic 和 OpenAI 兼容接口的 usage，放进 `AssistantMessage.usage`。
- `src/cli.ts`：`/compact`；自动压缩打印「正在压缩上下文」和压缩前后估算。
- `src/server/session.ts`、`src/server/http.ts`、`src/web/`：`POST /api/compact`、状态栏「正在压缩上下文」、右上角「压缩」按钮、成功后的 notice。
- `src/agent/compact.test.ts`、`src/server/session.test.ts`：覆盖上面「测试」一节的条目。

和设计稿的差异：

- 终端没有交互式中止。`LlmClient` 目前只带 120 秒超时，没有把 Ctrl-C 传成 abort，所以「用户中止压缩」这一条暂时不会发生；失败计数只在真正失败时增加。
- 阈值按固定常量算：摘要输出预留 20000，自动缓冲 13000，只让 `AGENT_CONTEXT_WINDOW` 改窗口。源码还会按模型的实际最大输出做 `min`，这里只接一个 provider 配置，先不做。
- 摘要请求的 `max_tokens` 沿用主会话配置（`AGENT_MAX_TOKENS`），没有单独开到 20000，避免超过小模型的上限。
- 网页会话也开始追加 `.copy-agent/session.jsonl`（此前只有终端写），这样压缩后仍能查原文。压缩前已经写过的内容不会被改写或删除。
- 摘要结构按这份文档的 6 节写（源码是 9 节），仍然保留 `<analysis>` / `<summary>` 两段，分析段在落库前丢掉。
